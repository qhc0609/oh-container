# 我在这台鸿蒙手机上从零写了个容器，然后把 Claude Code 跑了进去

> OpenHarmony 容器实战 · 第 1 篇
> 全部命令都在真机上跑过，报错原文照抄。
> 代码：github.com/qhc0609/oh-container

---

凌晨一点，我盯着手机屏幕上的一行报错。

```
unshare: Invalid argument
```

不是权限问题。`id -u` 是 0，`CapEff` 是全 capability，SELinux 是 Permissive 关着的。

不是命令写错了。`unshare -m` 同样的写法，返回 0，成功。

就是 `-p` 这一个参数，无论怎么试，都是 `Invalid argument`。

后来我明白了：**这台手机的内核里，压根没有 PID namespace 这个东西。** 不是没开，不是配置错，是编译内核的时候就没编进去。

而 Docker 的全部地基，就是它。

> 【配图 1】终端里 `unshare -p true` 报 `Invalid argument` 的截图

## 先说我要做什么

我有一台鸿蒙手机，USB 插在电脑上，能用 `hdc shell` 进去。

我想在这台手机上跑 Claude Code——就是那个能在终端里读写文件、跑命令的 AI 编程助手。后端不用 Anthropic，用我自己的 DeepSeek key。

目标只有一句话：

**`hdc shell` 进去，落在根目录 `/`，敲 `claude`，直接能用。**

听起来像"装个软件"。实际做下来是：从零写一个容器运行时，绕开三个内核缺失，踩了十几个坑，最后把 839MB 的环境塞进手机。

这篇讲第一段：**容器**。

## 一、先别急着动手：现成方案为什么全不行

动手之前我把能想到的路都试了一遍，省得白干。

**Termux？** 那是 Android 的东西。OpenHarmony 不是 Android，没有 `/system/bin/sh` 之外的包管理，没有 apt，没有 Termux 的生态。你能用的只有系统自带的那点 toybox。

**Docker / podman / LXC？** 依赖 PID namespace 和 cgroup。这台设备上 PID namespace 不存在。这条路是死的，早点认。

**proot？** 用户态模拟，靠 `ptrace` 拦截系统调用。理论上能用，但性能掉一半，而且 `ptrace` 在某些 SELinux 策略下会被拦。我要跑的是 Node.js，不是 shell 脚本，性能掉一半不能接受。

**chroot 就够了？** 这个方向对，但只有 chroot 不够。没有 mount namespace 的话，容器里挂载 `/proc` 会直接覆盖宿主的 `/proc`——手机当场抽风。

结论：**自己写。**

不是炫技。是这四条路里，只有最后一条能走通。

| 方案 | 为什么不行 |
|---|---|
| Termux | 鸿蒙不是 Android，生态不通用 |
| Docker / runc / podman | 内核没有 PID namespace |
| proot | 用户态 ptrace 模拟，性能腰斩 |
| 只有 chroot | 挂载会传播回宿主，危险 |
| **mount ns + uts + ipc + chroot** | **能用，就是本文** |

## 二、三十秒摸清这台设备的底牌

别猜。猜错了要返工两小时。

我这台：

```
OpenHarmony-4.0.10.13        (API 10)
TaiHang2102
Taihang_TX_V2.00.58
Linux 5.10.79 aarch64
```

`uname -a` 完整输出：

```
Linux localhost 5.10.79 #1 SMP PREEMPT Thu May 22 12:57:34 CST 2025 aarch64
```

自己查：

```powershell
hdc shell param get const.ohos.fullname
hdc shell param get const.ohos.apiversion
hdc shell param get const.product.software.version
hdc shell uname -a
```

然后重点看三件事。

### 第一件：你是不是 root

```sh
$ id -u
0

$ grep CapEff /proc/self/status
CapEff:000001ffffffffff

$ grep Seccomp: /proc/self/status
Seccomp:0

$ cat /sys/fs/selinux/enforce
0
```

四行，全是好消息。

`0` 是 root。`000001ffffffffff` 是全 capability——意味着能 `mount`、能 `chroot`、能改路由、能挂 `proc`。`Seccomp: 0` 说明没有系统调用过滤。SELinux `0` 是 Permissive，只记日志不拦。

**没有这个前提，后面一个字的活都干不了。** 很多设备上 `hdc shell` 只是普通用户，`mount` 直接 `EPERM`，那就到此为止。

### 第二件：`/data` 能不能执行二进制

```sh
$ mount | grep ' /data '
/dev/block/sda63 on /data type f2fs (rw,lazytime,seclabel,nosuid,nodev,noatime,background_gc=on,discard,no_heap,user_xattr,inline_xattr,acl,inline_data,inline_dentry,flush_merge,extent_cache,mode=adaptive,active_logs=6,alloc_mode=default,fsync_mode=posix)
```

一长串参数，眼睛只需要抓三个词：`nosuid`、`nodev`、**有没有 `noexec`**。

`/data` 是 `rw`，有 `nosuid` `nodev`，**没有 `noexec`**。

能执行。可以用。

顺手看 `/storage`：

```sh
$ mount | grep ' /storage '
tmpfs on /storage type tmpfs (rw,seclabel,nosuid,nodev,noexec,size=3760872k,nr_inodes=940218,mode=755)
```

带 `noexec`。

**rootfs 千万别放 `/storage`。** 放进去之后所有二进制都跑不起来，报 `Permission denied`，你会以为是 chmod 没给对，改半天权限，其实是挂载参数。这个坑很贵。

### 第三件：系统自带什么工具

```sh
$ for c in chroot pivot_root unshare nsenter busybox tar; do printf '%-12s %s\n' "$c" "$(command -v $c)"; done
chroot       /bin/chroot
pivot_root   /bin/pivot_root
unshare      /bin/unshare
nsenter      /bin/nsenter
busybox      /bin/busybox
tar          /bin/tar
```

`chroot`、`unshare`、`busybox` 全在。这就是全部原料，够了。

## 三、namespace 实测：能用的只有四个

这是整个方案的地基。**必须实测，不能查文档。**

```sh
$ ls /proc/self/ns/
cgroup
ipc
mnt
net
time
time_for_children
uts
```

七项。

**没有 `pid`。没有 `user`。**

`/proc/self/ns/` 这个目录是最权威的判断依据——内核如果没编译某个 namespace 的支持，这个符号链接压根不会创建。`ls` 一下就知道底牌，不用试、不用猜、不用找 `/boot/config`（手机上也没有）。

再确认一遍：

```sh
$ unshare -p true
unshare: Invalid argument
exit=1

$ unshare -U true
unshare: Invalid argument
exit=1

$ unshare -m true
exit=0
```

`-m` 成功，`-p` 和 `-U` 都是 `EINVAL`。

> **这里有个容易上当的地方**：`unshare --help` 里 `-p` 明明写着，busybox 的帮助文本也列出来了。但那是**工具**支持这个参数，**内核**不支持创建这种 namespace。工具和内核是两回事。busybox 是通用编译的，参数全都有；内核是厂商按需裁剪的。

结论：

| namespace | 状态 | 能干什么 |
|---|---|---|
| `mnt` | 可用 | 容器里的挂载点宿主看不见 |
| `uts` | 可用 | 容器能有自己的 hostname |
| `ipc` | 可用 | 独立共享内存 / 信号量 |
| `net` | 可用 | 能开，但本方案**不开**，直接用宿主网络 |
| `time` | 可用 | 没用到 |
| **`pid`** | **不可用** | 没有 PID 1，进程列表和宿主共享 |
| **`user`** | **不可用** | 不能 rootless，容器内 root 就是宿主 root |

所以这是一个「**mount + uts + ipc 隔离 + chroot 切根**」的容器，不是 Docker。

它没有 PID 隔离。你在容器里敲 `ps`，看到的是整台手机的进程。它也不能做 init 回收，容器里的孤儿进程会被宿主收养。

想清楚这一点，后面所有设计就顺了。

我把这个探测写成脚本了，换设备直接跑：`scripts/check-namespace.sh`。

## 四、rootfs：在电脑上下载，推到手机

容器得有个真的 Linux 根文件系统。我选 Alpine——官方 minirootfs 压缩包 3MB，解压 8MB，`apk` 生态完整，musl 静态二进制在 ARM64 上跑得很干净。

**但这里有个反直觉的地方：你不能在手机上直接下载。**

我试过。宿主机上没有 `curl`：

```sh
$ command -v curl
（空）
```

那就用 `busybox wget`？也不行：

```sh
$ busybox wget --spider https://dl-cdn.alpinelinux.org/alpine/v3.21/releases/aarch64/
wget: bad port 'https'
```

**这台设备的 busybox 编译时没带 HTTPS 支持。** 它把 `https` 当成端口号去解析了。

所以正确的路径是：**在电脑上下载，用 `hdc file send` 推过去。**

```powershell
# 1. 电脑上下载
curl.exe -LO https://dl-cdn.alpinelinux.org/alpine/v3.21/releases/aarch64/alpine-minirootfs-3.21.3-aarch64.tar.gz

# 2. 推到手机
hdc file send .\alpine-minirootfs-3.21.3-aarch64.tar.gz /data/local/tmp/alpine.tar.gz
```

然后在手机上解压：

```sh
mkdir -p /data/ohc/rootfs/claude
tar -xzf /data/local/tmp/alpine.tar.gz -C /data/ohc/rootfs/claude
```

验证：

```sh
$ chroot /data/ohc/rootfs/claude /bin/sh -c 'cat /etc/alpine-release'
3.21.3
```

能打出 `3.21.3`，地基就成了。

> 一旦容器建好，里面就有 `curl` 了（`apk add curl` 装的），后面所有下载都在容器里做，不受这个限制。卡住的只有最开头这一次。

## 五、写运行时：核心其实只有 30 行

网上讲容器原理的文章都爱从 cgroup 讲起，讲半天 OCI 规范。我这台设备上 PID namespace 都没有，讲那些没用。

真正的核心就一件事：**在新 namespace 里挂好文件系统，然后 chroot，然后 exec。**

`bin/ohc` 的 `run` 子命令：

```sh
cmd_run() {
    _name="$1"; shift
    ensure_net                      # 补默认路由，见第六节
    exec unshare -m -u -i "$OHC_SELF" __inner "$_name" "$@"
}
```

三个参数：`-m` mount、`-u` uts、`-i` ipc。

**关键是这里没有 `-f`。**

`-f` 是 fork。加了 `-f`，`unshare` 会 fork 一个子进程去当"容器里的第一个进程"，父进程退出。

听起来很对，但对交互式程序是灾难：子进程的 stdin/stdout 已经不是原来那个 TTY 了。`claude` 一起来就报 `not a terminal`，或者干脆黑屏卡死。

我一开始就是照着网上教程写的 `unshare -m -u -i -p -f`，结果 claude 一次都没起来过。

去掉 `-f` 和 `-p` 之后：

**进程号不变，文件描述符不变，TTY 还是原来那个 TTY。**

反正没有 PID namespace，也不需要谁来当 PID 1。这个"缺陷"在这里反而成了便利。

> Docker 那一大堆 `-t` `-i` 的逻辑，本质都是在解决 fork 之后 TTY 丢失的问题。我们不需要 fork，所以不需要那套东西。

然后是 `__inner`，真正干活的地方：

```sh
cmd_inner() {
    _name="$1"; shift
    _rootfs="$OHC_ROOT/rootfs/$_name"

    # 1. 独立 hostname（已经在新 uts ns 里了，改不到宿主）
    hostname "$_name"

    # 2. 挂载树私有化，防止容器里的挂载传播回宿主
    mount --make-rprivate /

    # 3. 挂文件系统
    mount -t proc proc   "$_rootfs/proc"
    mount --bind /sys    "$_rootfs/sys"
    mount --rbind /dev   "$_rootfs/dev"
    mount -t tmpfs tmpfs "$_rootfs/tmp"

    # 4. 工作目录：宿主 /data/ohc/workspace -> 容器 /work
    mount --bind "$OHC_ROOT/workspace" "$_rootfs/work"

    # 5. 加载环境变量（关键：set -a）
    set -a; . "$OHC_ROOT/containers/$_name/env"; set +a
    export HOME=/root

    # 6. 切根执行
    exec chroot "$_rootfs" /bin/sh -c 'cd "$1" 2>/dev/null || cd /; shift; exec "$@"' \
        ohc /work "$@"
}
```

四个地方值得单独说。

### `--rbind` 而不是 `--bind`

`bind` 只挂一层。`/dev/pts` 是 `/dev` 下面的**子挂载**，不会被带进来。

结果就是容器里没有 `/dev/pts/0`，`claude` 一启动就崩，报错还特别含糊。

用 `rbind` 递归挂，`pts` 跟着进来，TTY 就有了。

### `mount --make-rprivate /`

不写这一行，容器里做任何挂载都可能**传播回宿主**。

轻则宿主的 `/proc` 被覆盖，重则整机卡死要长按电源键。这一行是保命的。

### `set -a`

这个坑我卡了整整两个小时。

`source` 一个文件，里面的 `VAR=value` 会变成**当前 shell 的局部变量**。但当前 shell 马上就要 `exec` 成 `claude` 了，`exec` 只继承**被导出（exported）**的变量。

所以 `ANTHROPIC_AUTH_TOKEN` 在 shell 里 `echo` 明明有值，`claude` 进程里就是空的。表现是：

```
Not logged in · Please run /login
```

你会以为是 key 错了，去重新生成 key、重新配，配八遍都一样。真正的原因是一个你根本不会怀疑的地方。

`set -a` 的意思是"从现在开始，所有赋值的变量自动 export"。`set +a` 关掉。

### `HOME` 必须强制成 `/root`

`hdc shell` 这个环境里 `HOME=/`。因为 uid 是 0，家目录就是 `/`。

这个值会一路继承进容器。于是 `claude` 认为自己的家目录是 `/`，把配置写到 `/.claude.json`——容器的根目录。

后果不是立刻报错，是**行为诡异**：每次启动都问"是否信任这个目录"，点过还问，换个工作目录配置全丢。

强制 `export HOME=/root` 之后，一切正常。

## 六、那个让人怀疑人生的网络问题

容器起来了，`curl https://api.deepseek.com` 卡住不动。

DNS 能解析，TCP 出不去。

```sh
$ netstat -rn
Kernel IP routing table
Destination     Gateway         Genmask         Flags   MSS Window  irtt Iface
192.168.76.0    0.0.0.0         255.255.255.0   U         0 0          0 wlan0
```

**只有链路路由，没有默认路由。**

`192.168.76.0/24` 是本地网段，所以能 ping 通路由器。但目标地址不在这个网段时，内核不知道往哪送，直接丢掉。

补一条：

```sh
route add default gw 192.168.76.15 dev wlan0
```

补完立刻通了：

```sh
$ netstat -rn
Kernel IP routing table
Destination     Gateway         Genmask         Flags   MSS Window  irtt Iface
0.0.0.0         192.168.76.15   0.0.0.0         UG        0 0          0 wlan0
192.168.76.0    0.0.0.0         255.255.255.0   U         0 0          0 wlan0
```

这个毛病在 OpenHarmony 上不是偶发，是常态——WiFi 连上了、DHCP 拿到地址了，默认路由就是没写进去。

所以我把它做成幂等自检，每次 `ohc run` 都跑一遍：

```sh
ensure_net() {
    netstat -rn 2>/dev/null | grep -q '^0\.0\.0\.0' && return 0
    route add default gw "${OHC_GATEWAY:-192.168.76.15}" dev "${OHC_IFACE:-wlan0}"
}
```

有就跳过，没有就补。网关地址可以用 `OHC_GATEWAY` 覆盖。

## 七、toybox 的两个脾气

写脚本会撞上两件莫名其妙的事。

### 第一，没有 awk

```sh
$ awk 'BEGIN{print "awk ok"}'
awk: inaccessible or not found
exit=127
```

toybox 把它精简掉了。但 `busybox` 是完整的，里面有 awk。所以运行时里所有用到 awk 的地方都做了兜底：

```sh
_awk() { if command -v awk >/dev/null 2>&1; then awk "$@"; else busybox awk "$@"; fi; }
```

### 第二，grep 读管道会报错

```sh
$ netstat -rn | grep '0.0.0.0'
grep: (standard input): Invalid argument
```

注意：**它一边报错，一边还是把结果打出来了。**

```sh
grep: (standard input): Invalid argument
0.0.0.0         192.168.76.15   0.0.0.0         UG        0 0          0 wlan0
```

这个行为很阴。你的脚本如果判断的是 `$?`，可能还能跑；如果看的是 stderr 有没有输出，就会误判成失败。更离谱的是读普通文件也会这样：

```sh
$ grep CapEff /proc/self/status
grep: /proc/self/status: Invalid argument
CapEff:000001ffffffffff
```

绕法一样，退回 busybox：

```sh
_grep() { if command -v grep >/dev/null 2>&1; then busybox grep "$@"; else grep "$@"; fi; }
```

这两件事在任何文档里都查不到。你不实际在这台机器上写脚本，永远不会知道。

## 八、容器里到底装了什么

装完 Node 和两个 AI 客户端，`/data/ohc/rootfs/claude` 的构成（实测）：

| 内容 | 版本 | 体积 |
|---|---|---|
| Alpine base | 3.21.3 | 约 8 MB |
| Node.js | v22.23.4 | 约 110 MB |
| npm | 10.9.1 | — |
| `@anthropic-ai/claude-code` | 2.1.316 | **298 MB** |
| `opencode-ai` | 1.19.5 | **208 MB** |
| ripgrep | 14.1.1 | — |
| bash | 5.2.37 | — |
| `usr/` 合计 | | **600 MB** |
| **rootfs 总计** | | **839 MB** |

装的时候是一条命令的事。在容器里跑：

```sh
apk update
apk add --no-cache nodejs npm bash curl ca-certificates ripgrep libstdc++ gcompat git

node -v      # v22.23.4
npm -v       # 10.9.1

npm install -g @anthropic-ai/claude-code
npm install -g opencode-ai
```

**这里能省 202MB。**

`opencode-ai` 这个 npm 包会同时装 glibc 和 musl 两份原生二进制，各 200MB 出头。Alpine 是 musl，glibc 那份永远用不上：

```sh
rm -rf /usr/local/lib/node_modules/opencode-ai/node_modules/opencode-linux-arm64
```

删之前先确认剩下的那份还能跑，删之后再确认一次：

```sh
$ opencode --version
1.19.5
```

还有一处：npm 的缓存会涨到 484MB。

```sh
npm cache clean --force
rm -rf /root/.npm
rm -rf /var/cache/apk/*
```

三刀下去，rootfs 从 1.0G 掉到 839M。

## 九、目录长什么样

设备上最终是这样：

```
/data/ohc/
├── bin/
│   ├── ohc                  # 容器运行时，POSIX sh，约 10KB
│   ├── ohc-claude           # 启动 claude 的入口
│   ├── ohc-setkey           # 写 DeepSeek Key
│   └── ohc-verify           # 端到端自检
├── rootfs/claude/           # 就是上面那个 Alpine，839MB
├── containers/claude/env    # 环境变量（含 key，权限 600）
├── workspace/               # 容器内 /work 的实体
└── logs/
```

`workspace` 这个设计很重要。

它在 `/data` 下，重启不丢，而且被 bind 进容器当 `/work`。也就是说 **claude 在容器里改的文件，宿主上直接在 `/data/ohc/workspace` 能看到**。

容器删了，代码还在。

```
namespace 支持:
  mnt : 可用

  user : 不可用（内核未开启）

默认路由    : 0.0.0.0  192.168.76.15  0.0.0.0  UG  wlan0
```

进容器看看：

```sh
$ /data/ohc/bin/ohc run claude -- sh -c 'hostname; cat /etc/alpine-release; node -v; claude --version; pwd'
claude
3.21.3
v22.23.4
2.1.316 (Claude Code)

```

五项全对：

- Alpine 3.21.3——rootfs 正确
- Node v22.23.4——运行时在
- claude 2.1.316——客户端在
- `pwd` 是 `/work`——bind 挂载生效

再确认 chroot 真的生效了：

## 到这里你有了什么

一个能在鸿蒙手机上跑的容器。能切根、能隔离挂载、有独立 hostname、有独立 IPC、有持久化工作目录。

它没有 PID 隔离，不能当多租户平台用。但**在自己手机上跑开发工具，完全够**。

而且它只有 10KB——不是 10MB，是 10KB。一个 POSIX sh 脚本，没有依赖，没有守护进程，不需要 root 之外的特权。
