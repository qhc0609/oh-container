# 选题库：还能写什么

五篇成稿之外，这些是我想到但还没写的方向。按"爆款概率 × 可写性"排序。

---

## 1. 算账型：《手机跑 AI 编程助手，一个月电费多少？我把功率计插上了》

**钩子**：所有人都在讨论"能不能跑"，没人算"跑起来花多少电"。

**为什么能爆**：中文技术圈最缺的就是真实测量数据。绝大多数文章靠"据说""理论上"。你拿出功率计读数、连续 30 天的电表数据、和云服务器账单做对比，这个反差本身就有传播力。

**需要补什么**：
- USB 功率计（几十块）测充电功率
- 连续 7 天记录：待机 / 跑 claude 单次调用 / 长上下文任务
- 换算成月电费，对比一台 2 核 4G 云服务器（约 ¥60/月）
- 加一条：手机电池衰减的隐性成本（循环次数）

**难点**：测量要持续一周。但这是唯一能做出差异化的方式。

## 2. 对比型：《同一道题，DeepSeek / Claude / GPT 在我手机上跑，谁快谁准》

**钩子**：不吹参数，只看同一道真实题目。

**为什么能爆**：模型对比是永恒热点，但 99% 的对比是拿 benchmark 分数抄来抄去。你用**同一台手机、同一个客户端、同一段提示词**跑三家的实际表现，加上首字延迟、总耗时、token 消耗、代码能不能直接跑通，这是别人给不了的。

**需要补什么**：
- 三道题：一道算法（LeetCode 中等）、一道重构（给一段烂代码）、一道真实 bug（你自己项目里的）
- 记录：首字延迟、总耗时、输出 token、代码是否一次跑通
- 三家 key 都要有（DeepSeek 有，OpenCode 有，GPT 要买）

**风险**：容易被骂"测试不严谨"。所以要老实写清楚"这不是 benchmark，只是一次实测"。

---

## 3. 反向型：《我为什么不建议你在手机上跑 AI 编程助手》

**钩子**：所有人都在教你怎么装，我告诉你什么情况下别装。

**为什么能爆**：**反向选题的传播力通常是正向的三倍。** 因为它提供了"反对意见"，转发的人有了立场，评论区会吵起来，而吵起来就是流量。

**内容骨架**：
- 没有 PID 隔离 = 容器内 root 就是宿主 root，跑不可信代码等于把手机交出去
- 手机是通信工具，你把它搞成开发机，来电话了怎么办
- 839MB 存储 + 持续 CPU 占用对电池的伤害
- 屏幕 6 寸，改代码的体验上限就在那儿
- 真正适合的场景（三条），不适合的场景（五条）

**关键**：结尾不能只是唱反调，要给"什么人适合"的明确判据。否则显得哗众取宠。

---

## 4. 工具型：《手机变开发机的 7 个 hdc 命令，第 4 个能救命》

**钩子**：hdc 的文档烂到没人看，但这几个命令能省你几小时。

**为什么能爆**：工具类文章的收藏率极高。读者不一定转发，但一定收藏，而收藏在微信的算法里权重很高。

**七个命令**（都是实测有效的）：
1. `hdc list targets` —— 看设备，`Unauthorized` 怎么处理
2. `hdc file send` / `recv` —— 方向别搞反（我第一次就反了）
3. `hdc shell` 的 `HOME=/` 陷阱
4. **`hdc shell "echo \$PATH"`** —— 救命的那条：找到可写且在 PATH 里的目录，一切"怎么才能直接敲命令"的问题都解决了
5. `hdc install` / `uninstall`
6. `hdc hilog` —— 看系统日志，排查权限问题
7. `hdc shell param get const.ohos.fullname` —— 确认系统版本

**难点**：要确保每个命令都在你这台设备上真跑过，不能抄文档。

## 5. 逆向型：《一个 npm 包偷偷装了 202MB 用不上的垃圾》

**钩子**：`du -sh` 之后我愣住了。

**为什么能爆**：所有 Node 开发者都有 node_modules 焦虑。你把这个焦虑量化到一个具体数字上，还给出可复现的删法，共鸣极强。

**内容**：
- `opencode-ai` 同时装 glibc 和 musl 两份原生二进制
- 怎么发现的（`du -sh node_modules/* | sort -h`）
- 怎么确认哪份是垃圾（`ldd`、`file`、直接跑）
- 删了会不会出问题（实测：不会，但换到 Debian 就会）
- 举一反三：`sharp`、`esbuild`、`swc`、`prisma` 都有类似的平台包
- 通用瘦身脚本

**延伸钩子**：可以做成"npm 包瘦身"系列，每期拆一个包。

---

## 6. 标准型：《OpenHarmony 上没有 Docker，这件事该怪谁》

**钩子**：不是厂商偷懒，是取舍。

**为什么能爆**：这类文章容易引发行业讨论，被技术社区（尤其鸿蒙开发者群）大量转发。

**内容**：
- PID namespace 为什么在移动端内核里常被裁掉（内存开销、调度复杂度、安全攻击面）
- Android 也没有完整 namespace（有，但受限），iOS 完全没有
- 容器化在移动端的真实需求有多大
- 对比：Linux 桌面、服务器、嵌入式三者的取舍差异
- 结论：不是缺陷，是"移动端不需要"

**风险**：容易写成空谈。必须每一条都有实测或源码依据。

---

## 7. 场景型：《出差只带手机，我用它改完了线上 bug》

**钩子**：一个故事，不是一篇教程。

**为什么能爆**：**故事型内容在公众号的完读率远高于教程。** 读者不关心技术细节，关心"这事儿居然能成"。

**内容骨架**：
- 场景：高铁上，笔记本没电，线上告警
- 手机 + OTG 键盘（或者纯软键盘）
- `hdc shell` 需要电脑——**这是最大的障碍**，得解决：能不能手机自己连自己？（无线调试 / 本地 shell app）
- 实际改了什么 bug，花了多久
- 哪些操作在手机上极其痛苦（多文件跳转、diff 查看）
- 结论：能应急，不能日常

**难点**：必须真做一次，有真实截图和时间线。编的故事读者一眼看穿。

---

## 8. 极限型：《把 839MB 塞进手机：存储、内存、发热实测》

**钩子**：数字说话。

**为什么能爆**：硬件实测类内容在数码区有稳定流量，而且能跨圈——不只是程序员看。

**需要补什么**：
- 恢复前后可用存储变化
- 跑长任务时的内存占用曲线（`free -m` 每秒采样）
- 温度（`cat /sys/class/thermal/thermal_zone*/temp`）
- 有没有降频（对比任务前后的完成时间）
- 电池掉电速度

**优势**：这些数据你手上就有，采样脚本半小时能写出来。

## 9. 迁移型：《从 Termux 到鸿蒙：一个 Android 老兵的搬迁笔记》

**钩子**：我会的东西，在这里一半用不了。

**为什么能爆**：Termux 用户基数大，鸿蒙用户增长快，两拨人都在找"我在 Android 上那套东西怎么搬过来"。这个交叉点是空白。

**内容**：
- Termux 有的：pkg、proot、完整 Linux 用户空间
- 鸿蒙有的：toybox、busybox、chroot、unshare
- 一对一映射表：`pkg install` → `apk add`，`proot-distro` → 自己写 chroot
- 鸿蒙没有的：完整的 `/dev`、`/proc` 权限、后台进程保活
- 哪些习惯必须改

**难度**：需要真用过 Termux 一段时间，否则写出来是查资料的拼凑。

---

## 10. 教程型：《不用电脑，只用手机搭这套环境（可行吗？实测）》

**钩子**：整个系列都假设你有台 PC。没 PC 的人怎么办？

**为什么能爆**：直接扩大受众。而且"可行性验证"本身就是好内容——成功是教程，失败也是好文章。

**要解决的核心问题**：
- `hdc` 是 PC 端工具，手机上怎么跑？（有没有 Android/Harmony 版的 hdc 客户端？）
- 或者：能不能完全不用 hdc，用手机上的终端 app 直接操作？
- 下载 Alpine rootfs 需要解压工具
- 输入体验（软键盘敲 300 行 shell）

**结论大概率是"部分可行"**——这种诚实的部分结论比"完全可以"更有说服力。

---

## 11. 安全型：《你的 API Key 在手机里是怎么被看见的》

**钩子**：我随手 `grep` 了一下，全在里面。

**为什么能爆**：安全类内容天然高转发（"快看你有没有中招"）。

**内容**：
- 明文 key 在哪几个位置（`containers/claude/env`、`auth.json`、`.claude.json`、shell history）
- `chmod 600` 到底防住了谁（防住了非 root，防不住 root——而你就是 root）
- 备份包里是明文，传网盘等于公开
- 手机丢了怎么办
- 正确做法：短期 key、环境变量注入、加密备份、定期轮换
- 一个检测脚本：扫一遍所有可能泄露 key 的位置

**加分项**：给出"我现在怎么做的"——比如把 key 存 PC 上，用的时候才推过去。

## 12. 冷知识型：《toybox 没有 awk：OpenHarmony 脚本生存指南》

**钩子**：一条 `awk: inaccessible or not found` 让我重写了整个脚本。

**为什么能爆**：极客趣味强，容易被技术群转发。而且这类"踩坑合集"的长尾流量极好——半年后还有人搜到。

**内容**：
- toybox vs busybox 的取舍
- 缺 `awk` 怎么办（兜底函数）
- `grep` 读管道报 `Invalid argument` 的绕法
- `/tmp` 只读
- `tar` 不支持 socket
- `sed -i` 的行为差异
- `printf` 对 `\0` 的处理
- 一份"能在 toybox 上跑的 POSIX sh 子集"清单

**价值**：这篇会成为 OpenHarmony 开发者的常备参考。收藏率会很高。

## 13. 破案型：《装了 tmux 还是翻不动屏？我 grep 了 311MB 的二进制才找到真凶》

**钩子**：`history-limit` 调到 5 万，往上翻还是空白。问题不在 tmux，在 claude 自己。

**为什么能爆**：这是一个"所有人都以为自己会了、其实都错了"的坑。翻屏这件事，教程都写到"装个 tmux 就行了"就结束了，没人往下走一步。你把最后一步补上，读者会有"原来如此"的爽感——而且**立刻能用上**，不装环境也能验证。

**核心剧情**（三段递进，正好是三次误判）：
1. 第一反应：宿主控制台缓冲区太小 → 调 `BufferHeight` → 不但没用，窗口一放大就闪退（因为窗口宽 120 > 缓冲区宽 80，再设高度是非法的）。**教训：hdc 不是老实写字节流，它在 Windows 控制台上自己模拟一块固定尺寸的屏幕。**
2. 第二反应：装 tmux，历史归 tmux 管 → 会话能续上了，翻页还是空的。**教训：tmux 只能存"它看得到"的行。**
3. 真相：`busybox grep -a -o '1049h' claude.exe` → 1 次命中。`ESC[?1049h` 是切"备用屏幕"，备用屏幕按设计没有回滚历史，切走即丢。tmux 尊重这个切换，所以什么都没存下来。**一行 `set -g alternate-screen off` 解决。**

**最有说服力的素材**：同一个载荷（切备用屏幕 + 喷 200 行）跑两遍
```
默认 tmux（alternate-screen on）        history_size=0    LINE_rows=23
本机 .tmux.conf（alternate-screen off） history_size=177  LINE_rows=200
```
`177 = 200 - 24 + 1`，这个数字自己会说话。

**可复用方法论**（这是文章真正的价值）：
- 别猜，去 `grep` 二进制。控制序列不会说谎。
- 终端类问题永远分三层：程序以为自己多大 / 中间层允许多大 / 宿主实际画多大。任何一层错位，症状都是"显示不对"，但修法完全不同。
- `tmux capture-pane -S -500` 是照妖镜：它能看到的东西，用户就翻得到；它看不到，你把 `history-limit` 调到一百万也没用。

**风险**：`alternate-screen off` 有代价（退出后画面不还原、`Ctrl+B` 被 tmux 占用），要老实写出来，别装成银弹。

## 我的推荐顺序

如果只能再写三篇：

1. **第 3 篇（反向型）** —— 传播力最强，成本最低，你已经有一肚子素材
2. **第 5 篇（npm 瘦身）** —— 受众最广，跳出鸿蒙圈也能火
3. **第 12 篇（toybox 生存指南）** —— 长尾最好，会成为参考文档

第 1 篇（算账）和第 8 篇（实测）数据最有价值，但要花时间采数据，适合作为"月度大稿"。
