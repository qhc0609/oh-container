# 05｜我在一个 297MB 的二进制里 grep 出了两个官方文档没有的环境变量

> 系列第五篇，番外。不讲步骤，讲方法。
> 代码：`qhc0609/oh-container`

---

上一篇结尾留了个钩子，这篇拆开讲。

两件事：

一，**怎么从一个闭源 CLI 的二进制里，挖出它支持但没写文档的环境变量。**
二，**怎么在三十秒内判断一台陌生设备能不能跑容器。**

这两件事都比"照着教程配一遍"有用。因为教程会过期，方法不会。

---

## 一、起点：一个查不到答案的警告

claude 接上 DeepSeek 之后，每次启动都提示：

```
⚠ Model has unknown context window, some features may be limited
```

意思很清楚：它不认识 `deepseek-flash` 这个名字，不知道上下文窗口多大，所以某些功能（比如自动压缩对话历史）会保守处理。

烦。但更烦的是**找不到怎么关**。

翻官方文档，翻 GitHub issues，翻社区讨论，都没有。搜索"claude code unknown model context window"，出来的全是在问同一个问题的帖子，没有答案。

这说明一件事：**这个功能存在，但没写进文档。**

没写进文档，就一定在代码里。claude 是 npm 包，但核心是个编译好的二进制：

```sh
$ ls -lh /usr/local/lib/node_modules/@anthropic-ai/claude-code/
-rwxr-xr-x  1 root root  297M  claude.exe
```

297MB。Go 或者 Rust 编译出来的，符号表大概率没剥。

那就直接搜。

---

## 二、怎么搜二进制里的字符串

普通的 `grep` 不行，二进制里有大量 `\0`，`grep` 会认为是二进制文件然后输出 `Binary file matches`，不给你内容。

加 `-a`，强制当文本处理：

```sh
grep -a -o 'CLAUDE_CODE_[A-Z_]*' claude.exe | sort -u
```

`-o` 是"只输出匹配的部分"，`sort -u` 去重。

结果是一大串：

```
CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC
CLAUDE_CODE_MAX_OUTPUT_TOKENS
CLAUDE_CODE_MAX_CONTEXT_TOKENS
CLAUDE_CODE_DISABLE_UNKNOWN_MODEL_WINDOW_ENFORCEMENT
CLAUDE_CODE_USE_BEDROCK
CLAUDE_CODE_USE_VERTEX
CLAUDE_CODE_OAUTH_TOKEN
CLAUDE_CODE_ENTRYPOINT
CLAUDE_CODE_ADDITIONAL_DIRECTORIES
CLAUDE_CODE_DISABLE_TERM_BACKGROUND
...
```

六十多个。

其中**两个是我要的**：

```
CLAUDE_CODE_MAX_CONTEXT_TOKENS
CLAUDE_CODE_DISABLE_UNKNOWN_MODEL_WINDOW_ENFORCEMENT
```

第一个告诉它窗口多大，第二个直接关掉那个检查。

写进配置：

```sh
CLAUDE_CODE_MAX_CONTEXT_TOKENS=200000
CLAUDE_CODE_DISABLE_UNKNOWN_MODEL_WINDOW_ENFORCEMENT=1
```

警告消失。

> 顺便，这一串里还有几个文档里没有但很有用的：`CLAUDE_CODE_USE_BEDROCK`、`CLAUDE_CODE_USE_VERTEX`、`CLAUDE_CODE_MAX_OUTPUT_TOKENS`、`CLAUDE_CODE_ADDITIONAL_DIRECTORIES`。自己看需要。

## 三、为什么这招有效

因为**环境变量的名字必须留在二进制里**。

程序读环境变量，本质上是在查一张表。这张表里每一项都是一个字符串字面量：

```
"ANTHROPIC_BASE_URL"
"ANTHROPIC_AUTH_TOKEN"
"CLAUDE_CODE_MAX_CONTEXT_TOKENS"
```

编译器不会把这些字符串优化掉——它没法优化，因为运行时真要拿这个字符串去查 `environ`。

所以只要程序支持某个环境变量，**名字就一定会以明文出现在二进制里**。

这是闭源软件的一个结构性弱点。它想藏也藏不住。

### 换个语言，换个写法

不同技术栈，字符串的形态不一样：

| 技术栈 | 特征 | 搜法 |
|---|---|---|
| C / Go / Rust | 连续 ASCII，长度前缀或 `\0` 结尾 | `grep -a -o 'PREFIX_[A-Z_]*'` |
| Node.js（打包后） | 长字符串被切成多段，中间可能断开 | 搜更短的前缀，如 `PREFIX_` |
| Java | 常量池里 UTF-8，通常完整 | `strings` + `grep` |
| .NET | UTF-16LE，每个字符后面跟 `\0` | 搜 `P\0R\0E\0F\0I\0X\0` |
| 加密/混淆过的 | 运行时才拼出来 | 只能动态调试，静态搜不到 |

最后一种要留意。有些商业软件会把字符串加密，运行时解密到内存里。这种情况下静态搜不到，得上 `gdb` 或者 `frida` 挂上去看。

claude 这个没加密，属于第一种，最好办。

## 四、更通用的做法

上面那招只适合"知道前缀"的情况。不知道前缀怎么办？

**先找已经知道的那个，看它周围有什么。**

比如你知道 `ANTHROPIC_BASE_URL` 一定存在。找到它在文件里的位置，然后看前后几百字节：

```sh
grep -a -o '.\{0,200\}ANTHROPIC_BASE_URL.\{0,200\}' claude.exe | head -3
```

输出会把邻近的字符串一起带出来。同一个模块里的变量名，通常在内存里也挨着。

这招我用它找过很多东西：某个 CLI 的隐藏 debug 开关、某个 SDK 的私有 endpoint、某个客户端的内部超时配置。

### 还有一个方向：找错误信息

报错文本也是明文。而且报错文本往往比变量名更能说明功能存在。

```sh
grep -a -o '[A-Z][a-z ]\{20,80\}' claude.exe | grep -i 'context window'
```

从错误信息反推功能，再从功能反推开关。比正向找快。

### 别忘了 `strings`

有些二进制里字符串不是纯 ASCII，混了 UTF-8 或者被压缩过。`strings` 能过滤出可打印序列，比 `grep -a` 更宽容：

```sh
strings -n 8 claude.exe | grep -E '^[A-Z][A-Z0-9_]{6,}$' | sort -u
```

`-n 8` 是"只输出长度 ≥8 的可打印序列"，能滤掉大量噪音。

**在手机上跑这个要注意**：297MB 的文件，`strings` 会把整个文件读一遍，Cortex-A55 上大概要跑两三分钟。跑一次就够了，结果存下来。

## 五、第二个话题：三十秒判断一台设备能不能跑容器

这个更实用。

你手上可能有别的设备——另一台鸿蒙、一台 Android、一台嵌入式板子。想在上面跑容器，第一步不是装东西，是**判断能不能**。

### 第一步：看 `/proc/self/ns/`

```sh
ls /proc/self/ns/
```

输出里有什么，就支持什么。这是唯一可信的判断依据。

```
cgroup  ipc  mnt  net  time  user  uts
```

七项。少了 `pid`，少了 `user`。

**为什么这个目录这么权威？**

Linux 的 namespace 在 `/proc/<pid>/ns/` 下每个类型一个符号链接，指向一个 `nsfs` inode。内核如果没编译某个 namespace 的支持，这个链接压根不会创建。

所以 `ls` 一下就知道底牌。不用试、不用猜、不用看 `/boot/config`（手机上也没有）。

### 第二步：别信 `unshare --help`

```sh
$ unshare --help
BusyBox v1.36.1 multi-call binary.
Usage: unshare [-muinU] [-p PID] [-r] PROG [ARGS]
```

`-p` 明明在帮助里。但：

```sh
$ unshare -p true
unshare: unshare failed: Invalid argument
```

`EINVAL`。

原因是 `unshare` 这个**工具**支持 `-p` 参数，但**内核**不支持创建 PID namespace。工具和内核是两回事。`busybox` 是通用编译的，参数全都有；内核是厂商定制编译的，功能按需裁剪。

**所以判断依据永远是 `/proc/self/ns/`，不是帮助文本，不是文档，不是别人说的。**

### 第三步：看挂载参数

```sh
mount | grep -E ' /data | /storage '
```

三个参数要看清：

- **`noexec`** —— 这个分区上的文件不能执行。rootfs 放这儿，所有二进制都跑不起来，报 `Permission denied`，你会以为是权限问题。
- **`nosuid`** —— setuid 位无效。容器里想用 `su`、`passwd` 这类东西会失效。
- **`nodev`** —— 设备文件无效。一般不影响。

我这台设备：`/data` 是 `nodev,nosuid`（没 `noexec`，能用），`/storage` 带 `noexec`（不能用）。

**这个检查必须在动手之前做。** 我见过有人在 `noexec` 分区上搭了两小时，最后所有命令都报 `Permission denied`，一直以为是 chmod 没给对。

### 第四步：看 capability 和 SELinux

```sh
grep -E 'CapEff|Seccomp' /proc/self/status
cat /sys/fs/selinux/enforce
```

`CapEff: 000001ffffffffff` 是全 capability。这种值说明你在这个环境里几乎无所不能——能 `mount`、能 `chroot`、能改路由。

如果 `CapEff` 只有几位（比如 `00000000a80425fb`，那是普通进程的典型值），`mount` 会报 `EPERM`，容器做不了。

`enforce=0` 是 Permissive，SELinux 只记日志不拦。`enforce=1` 是 Enforcing，会拦——这时候 `chroot`、`mount` 都可能被拒，得先看 `dmesg` 里的 avc 拒绝记录。

### 三十秒清单

```sh
# 1. namespace 底牌
ls /proc/self/ns/

# 2. 权限
id -u; grep CapEff /proc/self/status; cat /sys/fs/selinux/enforce

# 3. 能写能执行的分区
mount | grep -E ' /data | /storage | / '

# 4. 工具在不在
for c in chroot unshare busybox tar; do printf '%-10s %s\n' $c "$(command -v $c)"; done
```

四条命令。跑完你就知道这台设备能不能做容器、能做到什么程度。

我把这四条整理成脚本了：`scripts/check-namespace.sh`。

## 六、一个反直觉的结论：缺功能不一定是坏事

回到 `unshare -p` 失败这件事。

按常规思路，这是缺陷。没有 PID namespace，容器就不是真容器：进程列表和宿主共享、没有 PID 1、不能回收孤儿进程、`ps` 一眼看穿所有东西。

但我最后发现，**正因为没有 PID namespace，这套方案才简单**。

理由：

有 PID namespace 的时候，创建它必须 `fork`。`fork` 之后，子进程是新的 PID 1，父进程退出。这时候子进程的 stdin/stdout 已经不是原来那个 TTY 了——你得自己做 pty 转发、自己做信号代理、自己处理窗口大小变化。Docker 那一堆 `-t` `-i` 的逻辑，全是为了解决这个。

没有 PID namespace，就不需要 `fork`。`unshare` 直接 `exec` 目标命令，**进程号不变，文件描述符不变，TTY 还是原来那个 TTY**。

一行 `unshare -m -u -i` 就够了。

所以我一开始试的是 `unshare -m -u -i -p -f`，`claude` 一起来就报 `not a terminal`。去掉 `-f` 和 `-p` 之后，立刻就正常了。

**约束反过来塑造了设计。** 这不是"妥协"，是在给定条件下找到的更短路径。

## 七、还有一个：toybox 和 busybox 的选择

OpenHarmony 自带两个 shell 工具集。

`toybox` 是 Android 系的血统，精简到极致：**没有 `awk`**。

```sh
$ awk '{print $1}'
awk: inaccessible or not found
```

`busybox` 是完整的，有 `awk`、有完整的 `grep`、有 `sed`。

但 `busybox` 的 `grep` 有个 bug：

```sh
$ netstat -rn | grep '^0.0.0.0'
grep: (standard input): Invalid argument
```

不是没匹配到，是**报错**。管道输入时会挂。

而 `toybox` 的 `grep` 读管道正常，只是读文件时有别的问题。

所以最终方案是"看情况选"：

```sh
_awk()  { if command -v awk  >/dev/null 2>&1; then awk  "$@"; else busybox awk  "$@"; fi; }
_grep() { if command -v grep >/dev/null 2>&1; then busybox grep "$@"; else grep "$@"; fi; }
```

`awk` 优先用系统的（有就用），没有退回 busybox。
`grep` 优先用 busybox（因为它读管道不崩），没有才用系统的。

这两个函数看起来土，但它们是在这台设备上写脚本能不能跑通的分界线。

**这类知识在任何文档里都没有。** 你只能自己撞上去，然后记住。

## 八、方法论总结

四句话。

**一、找不到答案就去二进制里找。** 环境变量名、错误文本、隐藏开关，只要程序支持，就一定是明文。`grep -a` 加 `-o`，先找前缀，再找邻居。

**二、判断能力看 `/proc`，不看文档。** `/proc/self/ns/` 有什么就是什么，`mount` 参数是什么就是什么，`CapEff` 是多少就是多少。帮助文本会骗你，文档会过期，别人说的可能不是这台设备。

**三、约束不是障碍，是设计输入。** 没有 PID namespace，所以不需要 fork，所以 TTY 天然保留。缺什么，往往同时告诉你该走哪条路。

**四、土办法能跑通就是好办法。** `_awk()` 和 `_grep()` 那种兜底函数，写出来不好看，但它是唯一能让脚本在这台设备上跑起来的东西。别追求优雅，追求能跑。
